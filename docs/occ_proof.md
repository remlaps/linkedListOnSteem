# Formal Proof of Correctness: Optimistic Concurrency Control (OCC)

To provide a formal proof of correctness for the Optimistic Concurrency Control (OCC) implemented in `steem_linked_list.py`, we must mathematically model the system and prove it satisfies the two fundamental properties of concurrency algorithms: **Safety** (the list remains consistent without forks) and **Liveness** (concurrent writers eventually succeed).

Here is the formal reasoning demonstrating that the OCC mechanism (`safe_append`, `safe_delete`, and `_is_orphaned`) is correct under a concurrent-honest-writer model.

---

## 1. System Model and Definitions

Let the Steem blockchain be an append-only ledger that provides a strict, immutable total ordering of all transactions.
*   **Total Order (<):** For any two transactions $tx_1$ and $tx_2$ on the blockchain, their physical location can be defined as a tuple of $(block\_num, trx\_num)$. We define $tx_1 < tx_2$ if $tx_1$ appears earlier in the blockchain than $tx_2$.
*   **Node (N):** A list operation broadcasted to the blockchain. Each node has:
    *   $N.seq$: The sequence number.
    *   $N.prev$: A pointer to the parent transaction.
    *   $N.loc$: Its physical location $(block\_num, trx\_num)$.
*   **Canonical Ordering (K):** The library deterministically resolves the "true" tail of the list by sorting all candidate nodes using the function:
    $K(N) = (N.seq,\ N.block\_num,\ N.trx\_num)$
*   **Canonical Chain (C):** The sequence of nodes generated by finding the node $T$ with the global maximum $K(T)$ in recent blocks, and recursively following $T.prev$ until a root is reached.

---

## 2. Theorem 1: Safety (Strict Linearizability)
**Claim:** If multiple clients concurrently attempt to append a node to the same tail, exactly one node will become part of the canonical chain, and all other clients will detect the collision and discard their orphaned nodes.

**Proof:**
1.  Suppose two clients, $A$ and $B$, both read the current canonical tail $T_{current}$ with sequence $s$.
2.  Both clients independently generate new nodes $N_A$ and $N_B$, where both assert $seq = s + 1$ and $prev = T_{current}.loc$.
3.  Both nodes are broadcasted and accepted by the blockchain. Because the blockchain guarantees a total order, they are assigned unique locations. Without loss of generality, assume $N_A.loc < N_B.loc$.
4.  Once the blocks are confirmed, both clients execute `_is_orphaned()`. This method queries the blockchain to find all recent candidate nodes, which will now include both $N_A$ and $N_B$.
5.  The system evaluates the canonical ordering function $K$:
    *   $K(N_A) = (s + 1, N_A.block\_num, N_A.trx\_num)$
    *   $K(N_B) = (s + 1, N_B.block\_num, N_B.trx\_num)$
6.  Because $N_A.loc < N_B.loc$, it is strictly true that $K(N_A) < K(N_B)$.
7.  The deterministic sort selects $N_B$ as the new canonical tail $T_{new}$.
8.  The function walks backwards from $T_{new}$ via the `prev` pointers. Since $N_B.prev$ points directly to $T_{current}$, the canonical chain is $[N_B, T_{current}, \dots]$.
9.  **Resolution:**
    *   Client $B$ checks if $N_B$ is in the canonical chain. It is. `_is_orphaned` returns `False`. Client $B$ succeeds.
    *   Client $A$ checks if $N_A$ is in the canonical chain. Because $N_B$ bypassed $N_A$ and pointed straight to $T_{current}$, $N_A$ is absent from the chain. `_is_orphaned` returns `True`.
    *   Client $A$ raises a collision exception, discards $N_A$ from its local state, and triggers a retry.

$\blacksquare$ *Therefore, forks are impossible. The list state resolves to a single unified chain, preserving safety.*

---

## 3. Theorem 2: Safe Deletion (Idempotency)
**Claim:** Concurrent `safe_delete` operations targeting the same node will safely resolve without creating redundant tombstones or corrupting the list.

**Proof:**
1.  Because `safe_delete` relies on appending a tombstone node to the tail of the list (Steem is immutable, so deletes are just standard appends), the conflict resolution is governed entirely by **Theorem 1**.
2.  If Client $A$ and Client $B$ both broadcast a tombstone for the node at sequence $X$, one tombstone (e.g., $D_B$) will win the canonical ordering race, and the other ($D_A$) will be orphaned.
3.  Client $A$ detects its tombstone $D_A$ is orphaned and initiates its fallback retry block.
4.  As part of the retry loop, Client $A$ performs a full `rebuild_index()` to establish the latest canonical state.
5.  Client $A$ parses the new canonical chain and observes Client $B$'s tombstone $D_B$, which marks target $X$ as `_deleted = True`.
6.  On the next iteration of the `safe_delete` loop, Client $A$ evaluates the target node. It sees the node is already flagged as deleted.
7.  The loop detects `attempt > 0` and `target.payload.get("_deleted")` is True, allowing it to deduce that a concurrent writer successfully deleted the node. It aborts the redundant broadcast and returns the existing tombstone.

$\blacksquare$ *Therefore, deletes are strictly idempotent and safe under concurrency.*

---

## 4. Theorem 3: Liveness (Lock-free Progress)
**Claim:** A client continuously attempting `safe_append` or `safe_delete` will eventually succeed with probability 1, avoiding livelock.

**Proof:**
1.  Assume a high-contention scenario where $N$ clients constantly collide.
2.  By Theorem 1, during *every* collision cycle, exactly one client is mathematically guaranteed to possess the highest `(block_num, trx_num)` sorting key.
3.  Thus, the system guarantees **global progress**: the canonical list will always grow by exactly 1 valid node per contention round.
4.  When the $N-1$ orphaned clients retry, they execute a backoff delay function: `wait_time * (1.5 ** attempt) + random.uniform(0, 3.0)`.
5.  This equation introduces an exponentially widening window of probability combined with continuous non-deterministic jitter.
6.  The probability of two clients choosing the exact same delay, landing in the exact same future Steem block, and looping infinitely approaches $0$ as the attempt counter increases.
7.  Because global progress is guaranteed (one winner always advances) and retry collisions probabilistically decay to zero, every individual client is guaranteed to eventually be the sole writer in a block or win the transaction ordering.

$\blacksquare$ *Therefore, the system provides probabilistic liveness and will eventually terminate successfully.*

---

## Conclusion

The Optimistic Concurrency Control (OCC) mechanism implemented in `steem_linked_list.py` is formally correct. 
* It uses the underlying blockchain's consensus ordering as a deterministic tie-breaker (Last-Write-Wins based on block/transaction indices).
* It verifies consistency by reading its own writes backward through the immutable `prev` pointer chain.
* It guarantees eventual success under contention via randomized exponential backoff.

*(Note: This proof assumes honest participants. Byzantine actors deliberately broadcasting invalid `seq` numbers could artificially manipulate the canonical tail, which is why the `enforce_single_author` parameter was importantly introduced in v0.0.2-alpha to protect the list).*
